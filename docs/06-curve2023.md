# Attack #06: Curve Finance (Vyper Bug) Exploit

## Overview

This document describes the simulation of the Curve Finance exploit that occurred in July 2023. The exploit was caused by a compiler bug in certain versions of Vyper (0.2.15, 0.2.16, and 0.3.0), which led to malfunctioning reentrancy guards, allowing attackers to drain several liquidity pools.

**Reference**: [Curve Vyper Exploit Post-Mortem](https://hackmd.io/@vyperlang/HJUgNMhs2)

## Attack Summary

- **Date**: July 2023
- **Amount Lost**: ~$73M US$
- **Affected Contracts**: Various Curve pools (alETH/ETH, msETH/ETH, pETH/ETH, CRV/ETH)
- **Attack Type**: Reentrancy (State / Read-only Reentrancy)
- **Root Cause**: Vyper compiler bug where the `@nonreentrant` decorator failed to prevent reentrancy across multiple functions sharing the same lock.

## Vulnerability Details

### The Vulnerability

The vulnerability stems from a bug in the Vyper compiler for versions 0.2.15, 0.2.16, and 0.3.0. The `@nonreentrant("lock")` decorator is supposed to create a mutex lock that prevents a contract from being reentered while a function is executing. 

However, due to a bug in how storage slots were allocated for these locks, functions that were meant to share the same lock (like `add_liquidity` and `remove_liquidity`) actually ended up with different lock variables. This meant that calling `remove_liquidity` locked `remove_liquidity` from being re-entered, but it did **not** lock `add_liquidity`.

### Attack Flow

The attacker leveraged this malfunctioning reentrancy guard to manipulate the pool's state and extract value:

**Step 1: Flashloan Funding**
- Flashloan 80,000 WETH from Balancer.
- Withdraw the WETH to native ETH.

**Step 2: Initial Liquidity Provision**
- Add 40,000 ETH as liquidity to the targeted Curve pool (e.g., pETH/ETH) using `add_liquidity`.

**Step 3: Trigger Reentrancy via `remove_liquidity`**
- Call `remove_liquidity` to withdraw the liquidity.
- The pool burns the LP tokens and sends the native ETH back to the attacker's contract.
- This ETH transfer triggers the attacker's `receive()` fallback function.

**Step 4: Reenter `add_liquidity`**
- Inside the `receive()` function (while `remove_liquidity` is still executing and hasn't finalized updating the pool's state), the attacker reenters the pool by calling `add_liquidity` again with another 40,000 ETH.
- Because of the Vyper bug, this call succeeds.
- Since the pool's internal balances and total supply haven't been fully updated from the `remove_liquidity` call, the `add_liquidity` calculation is based on an incorrect, manipulated state, minting the attacker disproportionately more LP tokens.

**Step 5: Extract Profit and Repay**
- After the initial `remove_liquidity` finishes, the attacker does a second `remove_liquidity` using the newly minted, artificially inflated LP tokens.
- This second removal extracts significantly more assets than were deposited.
- Swap the drained alt-assets (e.g., pETH) back to ETH.
- Wrap ETH back to WETH and repay the 80,000 WETH Balancer flashloan.

### Key Code Vulnerability

In the Vyper source code of the pool:

```vyper
@nonreentrant('lock')
def add_liquidity(amounts: uint256[N_COINS], min_mint_amount: uint256) -> uint256:
    # ...

@nonreentrant('lock')
def remove_liquidity(token_amount: uint256, min_amounts: uint256[N_COINS]):
    # ... Sends ETH to user -> triggers fallback
```

**The Problem:**
- The developer intended both functions to share the `'lock'` mutex.
- The Vyper compiler bug allocated different storage slots for `'lock'` in `add_liquidity` and `remove_liquidity`.
- An attacker could enter `remove_liquidity`, receive ETH, and from their fallback function re-enter `add_liquidity` because the lock for `add_liquidity` was never set.

## The Fix

### Post-Exploit Actions

1. **Vulnerability Disclosure**: The Vyper team acknowledged the compiler bug affecting versions 0.2.15, 0.2.16, and 0.3.0.
2. **Whitehat Rescue**: Several whitehat hackers and MEV bots front-ran some of the exploits, rescuing funds and returning them to the protocol.
3. **Compiler Patch**: The Vyper compiler bug was already fixed in version `0.3.1` (before the attack happened), but many legacy pools were still running on older, vulnerable versions.

### Proper Fix Implementation

For the affected pools, the fix involved migrating liquidity to new pools compiled with a patched version of Vyper (e.g., `0.3.1` or later) where the `@nonreentrant` decorator correctly shares the storage slot across multiple functions.

## Key Learnings

1. **Compiler Trust**: Smart contract security isn't just about the source code; the compiler can introduce vulnerabilities. Auditing the compiler and using up-to-date, stable versions is crucial.
2. **Reentrancy Variations**: Reentrancy doesn't always happen within the same function. Cross-function reentrancy and read-only reentrancy are significant threats when state is temporarily inconsistent.
3. **Immutability Trade-offs**: The inability to easily upgrade core DeFi primitives (like AMM pools) means that if a foundational bug is found, the only solution is often migrating liquidity, which is slow and chaotic during an active exploit.
4. **CEI Pattern**: Always adhering to the Checks-Effects-Interactions (CEI) pattern helps mitigate reentrancy even if the lock fails.
