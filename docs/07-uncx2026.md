# Attack #07: UNCX Smart Token Vesting Exploit

## Overview

This document describes the simulation of the UNCX Network Smart Token Vesting (VestingManager) exploit that occurred on October 14, 2026, resulting in the theft of approximately $86K-$89K USD across five ERC-20 tokens (EDGEN, ZC, pepecoin, LO0P, $PAAL), with ~$85.6K retained after flash-loan repayment.

**Reference**: [BeInCrypto - Hacker Pulls $86,000 in Locked Tokens From a Shared Crypto Vault](https://beincrypto.com/uncx-exploit-drains-token-vesting-pool/)

## Attack Summary

- **Date**: October 14, 2026
- **Amount Lost**: ~$86K-$89K US$
- **Affected Contract**: VestingManager (0xA98F06312b7614523d0f5e725e15fd20fB1b99F5)
- **Attack Type**: Shared-pool share-accounting drain
- **Root Cause**: `release()` pays a slice of the entire shared pool (not the position's own deposit), and `release()`/`cancel()` double-debit `_totalTokenShares`

## Vulnerability Details

### The Vulnerability

UNCX's Smart Token Vesting pools every deposit of a given token into a single VestingManager contract, tracking each position only by "shares". Three flaws combine to allow a permissionless drain:

**1. `release()` pays a slice of the ENTIRE shared pool, not the position's own deposit.**

```solidity
uint256 balance = IERC20(schedule.token).balanceOf(address(this));
uint256 amount  = (releasableShares * balance) / _totalTokenShares[schedule.token];
```

A position's payout scales with the full contract balance and with the global share denominator `_totalTokenShares`. Shrinking that denominator inflates every holder's payout fraction — including the attacker's own.

**2. `release()` and `cancel()` double-debit `_totalTokenShares`.**

```solidity
// release()
_totalTokenShares[token] -= releasableShares;
schedule.released += releasableShares;
// ...but never reduces the position's _depositedShares

// cancel()
vestedShare   = vestedAmount * _depositedShares[vestingId] / schedule.totalAmount;
sharesToRemove = _depositedShares[vestingId] - vestedShare;   // ignores schedule.released
_totalTokenShares[token] -= sharesToRemove;
```

Because `_depositedShares` still carries the shares already taken out by `release()`, `cancel()` debits those same shares from the global total a **second time**. The denominator is driven below the shares actually backed by the pool, so the surviving positions over-pay.

**3. A vesting whose tranche times are already in the past is 100% releasable immediately.**

```solidity
_getReleasableShares() vests by calculator.calculateVestedAmount(tranches, block.timestamp);
```

The attacker's create tranches end one second before the fork timestamp, so each created vesting is fully vested the moment it exists and can be released and cancelled inside the same transaction.

### Why This Breaks the Protocol

The mechanism is fully permissionless — `createVesting` / `createAirdropVesting` / `topUpVesting` / `cancel` / `release` carry no owner, role, or signature gate. Any address may create and manage its own vestings. The attacker is a plain EOA operating its own positions through its own contract.

## Attack Flow

Per token, the attacker:

1. **Flash-borrows working capital** from a liquidity source (Uniswap V3/V2 flash, or Uniswap V4 PoolManager).
2. **Creates one "payout" vesting** holding the real target amount.
3. **Creates one or two soft+topable "helper" vestings** and **releases** them — debiting `_totalTokenShares` while leaving `_depositedShares` intact.
4. **Optionally donates spare token** straight into the pool to raise the contract balance.
5. **Tops the helpers up and cancels them** — the second, double-counted debit of the same shares.
6. **Releases the payout vesting** against the now-corrupted denominator and the inflated balance, over-withdrawing the other vesters' backing tokens.
7. **Repays the flash loan** in the same leg.

## Key Code Vulnerability

The vulnerable accounting in `VestingManager.release()`:

```solidity
function release(uint256 vestingId) external {
    // ...
    uint256 releasableShares = _getReleasableShares(schedule);
    uint256 balance = IERC20(schedule.token).balanceOf(address(this));
    uint256 amount = (releasableShares * balance) / _totalTokenShares[schedule.token];
    // ...
    _totalTokenShares[schedule.token] -= releasableShares;
    schedule.released += releasableShares;
    // _depositedShares[vestingId] is NOT reduced here
}
```

And the double-debit in `cancel()`:

```solidity
function cancel(uint256 vestingId) external {
    // ...
    uint256 vestedShare = vestedAmount * _depositedShares[vestingId] / schedule.totalAmount;
    uint256 sharesToRemove = _depositedShares[vestingId] - vestedShare; // ignores schedule.released
    _totalTokenShares[schedule.token] -= sharesToRemove;
    // ...
}
```

## Mitigations

- **Track per-position deposits**: `release()` should compute the payout from the position's own deposited shares, not the entire shared pool balance.
- **Single-debit accounting**: `cancel()` must account for shares already released (`schedule.released`) so the global denominator is never debited twice.
- **Enforce a minimum share denominator**: prevent `_totalTokenShares` from being driven below the shares actually backed by the pool.
- **Gate privileged operations**: `createVesting`/`cancel`/`release` should carry appropriate access control where needed.
